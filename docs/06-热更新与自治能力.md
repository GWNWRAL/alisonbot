# 06 · 热更新与自治能力

AlisonBot 有两条「不用重启就能改」的路径，以及一套「让 Alison 自己动手」的自治能力。本文分别说明它们的原理、适用范围与**边界**——边界比能力更重要，因为它决定了你什么时候必须重启、什么时候不能放手。

## 一、热配置

「热配置」指：修改配置后，**进程内直接生效**。

三种修改途径效果一致：

| 途径 | 操作 |
| --- | --- |
| 直接编辑 | 改 `workspace/alison.yml` |
| 对话 | 在聊天里告诉 Alison 你要怎么改 |
| 控制中心 | 在「系统设置」面板里改 |

典型可热生效的内容：

- 模型提供方、baseURL 等模型相关设置；
- 平台开关与端口类设置；
- 记忆 / 日记 / 好感度等能力开关；
- 插件的启用与禁用。

## 二、热重载

「热重载」指：插件层面的变更在进程内应用，不需要重启进程。

| 动作 | 是否需要重启 | 由谁完成 |
| --- | --- | --- |
| 启用 / 禁用插件 | 不需要 | 你（控制中心）或 Alison |
| 安装新插件 | 不需要 | 你（控制中心）或 Alison |
| 修改插件相关配置 | 不需要 | 你或 Alison |
| 更换人设预设 | 通常不需要 | 你或 Alison |
| ChatLuna 预设的会话级缓存更新 | **需要重启** | 提示你手动重启 |

### 为什么少数改动必须重启

热更新的做法是「在运行中的进程里重新加载与重新应用配置」。但有些状态是**会话级**的，或者说需要整体重建才能一致——典型就是 ChatLuna 预设的会话级缓存。这类改动无法在保留现有会话的前提下安全替换，因此会提示你重启。

## 三、自治能力

自治由 `koishi-plugin-alison-autonomy` 提供，包含三类动作。

### 1. 自改配置

你说「回复太长了，短一点」，她改 `workspace/alison.yml` 并热生效——不需要你去翻文件。

### 2. 自装插件

你说「给我加个搜图能力」，她找到对应插件、安装、启用，并告诉你结果。

### 3. 自检修复

你说「QQ 连不上了，看看怎么回事」，她检查配置与依赖状态，尝试修复；修不了就告诉你卡在哪。

## 四、边界：什么会做，什么不会做

自治不等于放任。下面这些边界请务必理解：

**应当保持的边界**

- **授权范围**：自治动作应限定在你授权的范围内。范围外的动作应先征求你同意。
- **可回滚**：改配置属于可回滚动作；需要重启的改动她会提示而不是擅自重启。
- **不自作主张扩大暴露面**：例如不会擅自把网页平台从 `127.0.0.1` 改成对外开放。
- **不隐瞒失败**：测试失败、安装失败、修复失败都应如实反馈原因。

**明确做不到的事**

- **不能修复上游缺陷**：Koishi 4.18 与 ChatLuna 1.4 的行为由上游决定，她无法修改。
- **不能绕过需要重启的改动**：会话级缓存一类的问题只能提示重启。
- **不能让不兼容的插件变兼容**：兼容桥的能力边界见 [05-插件体系与多平台兼容.md](05-插件体系与多平台兼容.md)——依赖完整运行时的插件不会因为自治而变得可用。
- **不能替你承担风险决策**：是否对外开放端口、是否安装来源不明的插件，这类决定需要你自己拍板。
- **具体动作清单以实际版本为准**：哪些动作会先询问、哪些可以直接执行，属于实现细节，请以仓库中的实际实现为准；本文不逐条承诺。

## 五、实用建议

1. **改配置前备份 `workspace/alison.yml`**，尤其在让 Alison 代改的时候。
2. **把重要变更说清楚**：例如「把网页端口改成 5150 并告诉我新地址」，比「改下端口」更可靠。
3. **遇到反复失败先看日志**：自治修复失败通常意味着配置或环境问题，需要你提供信息。
4. **不要在生产环境放开自治**：先在小范围试用，确认行为符合预期。
5. **信任但验证**：改完之后在控制中心的系统设置里核对一眼。

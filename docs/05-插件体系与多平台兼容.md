# 05 · 插件体系与多平台兼容

AlisonBot 的设计原则是「微内核 + 一切皆插件」：内核只提供框架，能力全部以插件形式存在。本文说明四类插件、兼容矩阵，以及兼容桥能做到什么、做不到什么。

## 一、四类插件

### 1. Alison 插件（ICE 规范）

AlisonBot 自有的插件规范，存放在工作区：

```text
workspace/plugins/alison/<名字>/
└── plugin.json        # 插件清单
```

清单里声明插件的基本信息与能力入口。**字段定义以仓库中的规范定义为准**：本文不重复列举，以免与实际实现脱节。若清单格式有变化，请以仓库为准。

### 2. Koishi 插件

Koishi 生态的插件（含 ChatLuna 的模型适配器，例如 deepseek / qwen / 任意 OpenAI 兼容网关）属于这一类，按 Koishi 的方式安装即用。它们是**原生兼容**的：不需要兼容桥，能直接跑。

### 3. 多平台 Python 插件

为了让 AstrBot / NoneBot2 / MaiBot（maibot_sdk）/ LangBot 生态的插件能复用，AlisonBot 提供了兼容桥。目录约定：

```text
workspace/plugins/py/<框架>/<插件名>/
```

例如（`<框架>` 取值为 `astrbot`、`nonebot2`、`maibot`、`langbot` 等）。前提条件：本机需要安装 **Python 3.9 或更高版本**。

### 4. MCP server（Model Context Protocol）

MCP 是原生支持的：安装 `koishi-plugin-chatluna-mcp-client`，在配置中填入 `mcpServers` JSON，即可接入任意 MCP server 提供的工具。语言不限——MCP server 用什么语言写都可以。

```jsonc
// mcpServers 结构示意；实际字段名以该插件文档与仓库定义为准
{
  "mcpServers": {
    "example": {
      "command": "npx",
      "args": ["-y", "@example/mcp-server"]
    }
  }
}
```

## 二、兼容矩阵

| 平台 | 语言 | 兼容程度 |
| --- | --- | --- |
| Koishi / ChatLuna | JS | 原生：直接装、直接跑 |
| MCP（Model Context Protocol） | 任意 | 原生：装 `koishi-plugin-chatluna-mcp-client`，填 `mcpServers` JSON 即可接入任意 MCP server 的工具 |
| AstrBot | Python | 命令子集：`@filter.command` 等，走兼容桥 |
| NoneBot2 | Python | 命令子集：`on_command` / `on_keyword` / `on_startswith` / `on_message` |
| MaiBot（maibot_sdk） | Python | 命令子集：`@Command` / `@Action` / `@Tool` |
| LangBot 4.x | Python | 尽力而为：组件式，完整语义需要官方 Plugin Runtime |
| mirai-console | Java / Kotlin | 未支持（需要 JVM 旁路，规划中） |

读这张表时的要点：

- 「原生」= 不需要桥，行为与在原生框架中一致（仍受上游框架自身限制）。
- 「命令子集」= 只有一部分 API 被精确实现，见下文第三节。
- 「尽力而为」= 能加载、部分能跑，不保证完整语义。
- 「未支持」= 当前版本根本不能加载。

## 三、兼容桥的原理与边界

### 原理

兼容桥只**精确实现「注册命令」这一层 API**，其余 API 用宽容桩（auto-stub）兜底。

```text
Python 插件 import 框架 SDK
      ↓
兼容桥：命令注册 API → 真实实现（注册到内核）
        其它 API     → 宽容桩（auto-stub），调用不报错，返回占位值
      ↓
插件完成加载与命令注册
      ↓
用户触发命令 → 内核调度 → 「命令 → 文本回复」链路
```

之所以这样设计：绝大多数插件在**导入与注册阶段**就会调用大量框架 API。如果这些调用直接失败，插件根本加载不起来，连它能提供的命令也拿不到。用宽容桩兜住这些调用，插件就能走到注册阶段，把命令交出来。

### 能做到

- 插件能被加载，不因缺少框架 API 而在导入期崩溃；
- 注册的命令能被识别与触发；
- 「命令 → 文本回复」这条链路可用。

### 做不到

- **依赖完整运行时的插件不行**。如果插件的核心价值来自框架特有的调度、定时任务、持久化、事件总线、上下文对象或平台专有 API，宽容桩只能让它「不报错」，不能让它「真工作」。
- 需要框架数据库、权限系统、富媒体消息链等能力的插件，通常只能部分可用或完全不可用。
- LangBot 4.x 采用组件式设计，完整语义需要官方 Plugin Runtime；兼容桥只做尽力而为。
- mirai-console（Java / Kotlin）当前未支持，需要 JVM 旁路，属于规划中。

## 四、选择插件的建议

| 你的需求 | 推荐做法 |
| --- | --- |
| 想要稳定、完整的功能 | 优先用 Koishi 插件或 Alison 插件 |
| 想接入外部工具 | 优先用 MCP server（原生支持，语言不限） |
| 想复用已有 Python 插件 | 先确认它主要靠「命令 → 文本回复」，否则不要期待完整行为 |
| 想复用 mirai-console 插件 | 当前版本不可行，规划中 |

## 五、安装位置速查

| 插件类型 | 目录 |
| --- | --- |
| Alison 插件（ICE 规范） | `workspace/plugins/alison/<名字>/plugin.json` |
| 多平台 Python 插件 | `workspace/plugins/py/<框架>/<插件名>/` |
| Koishi / ChatLuna 插件 | 按 Koishi 的插件机制管理 |
| MCP server | 不需要放目录，在 `mcpServers` 配置中声明 |
